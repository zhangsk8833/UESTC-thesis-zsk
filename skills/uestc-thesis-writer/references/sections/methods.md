# 方法与工程实现

交代系统边界、已知量、待求量和约束；解释设计选择如何回应问题。按依赖关系描述模块输入输出、更新步骤和停止条件。关键推导说明数学依据，核对维度、索引和符号字体。提供可复现实现细节、计算与存储代价，实际代码与文字互相核对。工程效果不能只凭复杂度阶数或一个代码片段断言。

写前检查：本节目的、输入证据、前后关系是否清楚。写后检查：事实、引用、条件、符号与主张是否一致。材料不足的地方列具体问题，不用流畅文字掩盖。

## 从代码到论文的核对表
把一次实际运行的配置作为基准，记录入口、版本、随机性来源、数据预处理、训练/迭代过程和推理过程。逐一把论文中的模块对应到函数或类、输入输出形状和关键参数。论文写的是算法逻辑，不逐行翻译代码；但代码实际没有的分支、先验或约束不得作为既成方法描述。代码中遗留但未执行的模块不计入最终方案。

区分三种依据：数学推导说明性质；实现说明如何计算；实验说明在某条件下效果如何。三者互相支持但不能互相替代。例如，阶数较低不能直接推出实际延时更低，一段正确的损失函数代码也不能证明训练收敛。

## 小节组织
1. 给出本章要解决的具体问题及上一章提供的基础，避免重复整篇背景。
2. 定义系统、假设、观测量、未知量、目标与约束。说明实际场景中哪些假设能满足，哪些只是分析简化。
3. 用整体图或步骤概览交代数据流，之后按计算依赖说明各部分。图里的模块名称和正文、代码一致。
4. 对关键设计解释“为什么需要这一步”和“这一步怎样实现”。动机从真实问题推得，不能从好看的结果反向编造。
5. 给出可执行步骤、初始化、超参数、终止条件、训练与使用阶段差异。需要时提供伪代码，细节不得与公式冲突。
6. 讨论计算量、存储、适用条件和可能失败方式，为实验设计提出可检验问题。

这是一种组织选择，不要求每个方法章节拥有相同六个标题。若两个研究内容一前一后递进，写清共享前提和新增部分；不要重复抄写同一模型。

## 推导与符号
每个等号、不等号、近似和优化步骤要能说明所用定义、假设或定理。区分恒等、渐近、上界、局部近似与经验关系；不能把“约等于”改成“等于”来使语言简洁。注明取期望的随机变量与分布，解释边界条件和矩阵可逆等前提。

首次出现符号时交代含义、维度/单位和索引范围。向量、矩阵、标量、集合的字体保持语义一致；同一字母不要在邻近小节代表不同对象。多层下标需说明顺序。共享符号可建立全局表，但不能以“见符号表”代替关键式附近解释。

## 章末验收
只读本章能否知道输入、输出和如何计算？每一关键设计是否对应一个问题？核心公式是否能从已给前提得到？方法名称、算法框图和代码是否一致？本章声称的贡献中哪些将在何处被验证？缺失信息进入 issues，不用“具体设置如下”接空表。
